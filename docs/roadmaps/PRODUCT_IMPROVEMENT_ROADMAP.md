# Roadmap покращення Pullora

Оновлено: 8 серпня 2026 року.

Цей файл є джерелом правди для запланованих покращень Pullora після `v5.2.43`. План не залежить від історії чатів або пам'яті асистента.

## Основні правила

- Українська є мовою за замовчуванням.
- Усі нові тексти повинні мати український та англійський переклади.
- Не змінювати усталений темний дизайн без окремого рішення.
- Спочатку надійність і безпека, потім нові можливості.
- Не додавати залежності, якщо завдання вирішується засобами React, TypeScript, Rust або Tauri.
- Кожен користувацький реліз повинен пройти production-збірку, smoke-test і перевірку обох мов.

## Незмінний дизайн-контракт

Канонічний візуальний baseline Pullora — реліз `v5.10.1`, який відновлює перевірений дизайн `v5.9.0`. Усі наступні роботи з UI є внутрішньою уніфікацією, виправленням дефектів або оптимізацією, але не редизайном.

Обов'язково зберігати без візуальних змін:

- прозорі й розмиті підкладки, крізь які помітний загальний фон;
- чинну синю палітру, сині акценти, selection, focus і primary-дії;
- поточну композицію Library, ширину sidebar, hero card, панель основної дії, блоки версій і деталей;
- чинні відступи, висоти, радіуси, типографіку, іконки, щільність і візуальну ієрархію;
- чинну візуальну мову Settings, About, Install, контекстних і випадаючих меню; їхню структуру дозволено змінювати лише в межах окремо описаного релізу без нової айдентики;
- окремі темну та світлу теми як дві реалізації однієї айдентики, а не два різні продукти;
- незалежність загального фону, hero-фону й обкладинки застосунку.

Заборонено без окремого рішення користувача:

- змінювати палітру, стиль, композицію або пропорції в межах технічного рефакторингу;
- глобально перефарбовувати поверхні кольором обкладинки, hero-фону чи власного фону;
- замінювати наявну розмітку або CSS новою дизайн-системою одним великим кроком;
- вважати скорочення CSS достатньою причиною для зміни зовнішнього вигляду;
- позначати UI-пункт завершеним без порівняння з baseline-знімками.

Допустимі візуальні зміни: лише явно замовлене виправлення конкретного дефекту, доступність, читабельність або адаптація до підтримуваного розміру вікна. Така зміна повинна бути локальною й не змінювати решту екрана.

## v5.10.0 — єдина дизайн-система

Мета: усі теми, вікна, меню та інтерактивні стани Pullora використовують один набір правил замість локальних CSS-виправлень. Візуальний шар дозволено повністю перезбирати, але чинні сервіси, hooks, Tauri-команди, download queue, rollback і SHA-256 перевірки залишаються джерелом поведінки.

> Історичний запис. Реалізація спричинила неприйнятний візуальний дрейф і була повністю відкочена у `v5.10.1`. Позначки `[x]` нижче означають лише те, що робота входила до `v5.10.0`, а не те, що її реалізація збереглася після відкату. Її підхід із одночасною заміною всього візуального шару не можна повторювати; чинним джерелом вигляду є дизайн-контракт вище.

- [x] Для звичайної інсталяції Windows використовувати `%LOCALAPPDATA%\Pullora\Apps` як канонічну стандартну папку застосунків. `default_installation_path()` тепер використовує локальну директорію даних Windows, а нові settings одразу отримують цей шлях; точковий Rust-тест фіксує контракт.
- [x] Для portable-версії зберегти `<папка Pullora>\apps`, щоб лаунчер і встановлені застосунки можна було переносити разом. `default_installation_path()` для portable-збірки повертає `exe_dir.join("apps")`; чиста функція `portable_installation_path` покрита окремим Rust-тестом.
- [x] Не використовувати `Документи`, OneDrive або `Program Files` як автоматичний шлях: стандартна папка не повинна залежати від синхронізації хмари чи вимагати прав адміністратора. Дефолтний шлях уже будується через `dirs::data_local_dir()` (`%LocalAppData%`), а в кодовій базі не лишилось інших посилань на `document_dir`/OneDrive/Program Files; застарілий приклад `Documents\Pullora Apps` у тексті помилки `release.installPathRequiresWritable` замінено на `%LocalAppData%\Pullora\Apps` в `uk.ts` та `en.ts`.
- [x] Автоматично створювати стандартну папку безпосередньо перед першим завантаженням та перевіряти, що вона є директорією і доступна для запису. Спільну `ensure_installation_path` використовують і Settings, і всі входи в завантаження; зайвої файлової операції під час кожного запуску немає. Покрито Rust-тестом на створення відсутньої папки.
- [x] Якщо папку неможливо створити або вона недоступна для запису, не починати завантаження та запропонувати користувачу вибрати інший шлях із локалізованим поясненням. Перевірку перенесено з UI-майстра встановлення у саму Rust-команду `start_download` (`install_path_guard_error`), тому вона діє для всіх викликачів, включно з пакетним оновленням бібліотеки, яке раніше цю перевірку оминало. Non-installer asset із недоступною чи незаписуваною папкою одразу отримує стабільний код `errors.installPathRequired`/`errors.installPathUnavailable`/`errors.installPathRequiresWritable`, локалізований в `uk.ts`/`en.ts`; installer-асети толерантні до `requiresElevation`, бо пишуть через системний інсталятор. `ReleaseSelector` і далі пропонує кнопку вибору іншої папки на екрані підтвердження. Покрито двома Rust-тестами.
- [x] Перед використанням шляху перевіряти доступне місце на цільовому диску; якщо його недостатньо для завантаження та розпакування, не починати операцію й показати потрібний і доступний обсяг. Новий `storage::disk_space` читає вільне місце через `GetDiskFreeSpaceExW` без нової залежності; `disk_space_guard_error` використовує подвоєний розмір asset як просту оцінку завантаження та розпакування. Активна версія не додається вдруге, бо вона вже займає місце на диску, а безпечна заміна виконується через перейменування. Фронтенд показує локалізовані обсяги українською та англійською. Покрито Rust-тестами на нестачу й достатність місця.
- [x] Нормалізувати шлях і безпечно обробляти symlink/junction: `installation_root` канонізує найближчого наявного предка навіть для ще не створеної папки, тому всі операції отримують ефективний шлях. Junction у `Windows`, `Program Files` або `ProgramData` блокується як небезпечний, а `ensure_within` не дозволяє дочірньому junction вийти за вибраний root. Додано Windows-тест із реальними junction.
- [x] Виявляти заблоковану, read-only або зайняту іншим процесом папку до початку завантаження. Спільна перевірка створює й видаляє службовий файл без перезапису, розрізняє відсутність прав, Windows sharing/lock violation та інші помилки. Backend, Settings і Install використовують однакові стабільні стани й локалізовані пояснення українською та англійською; сирі файлові помилки не виходять у UI. Додано Windows-тест із реально заблокованим файлом.
- [x] Зробити backend єдиним джерелом ефективного шляху. `start_download` більше не приймає шлях від frontend і читає збережене значення зі спільного backend state, як update, rollback, cleanup та uninstall. Вибір папки в Install спочатку нормалізується й зберігається чинною командою Settings, яка повертає ефективний шлях у UI.
- [x] Не перезаписувати явно вибрану користувачем папку під час запуску, оновлення, зміни теми або скидання параметрів вигляду. Загальна команда `update_settings` ігнорує шлях із frontend та зберігає чинне backend-значення; змінити папку можна лише через окрему `set_installation_path`, яку тепер використовують поле й системний вибір папки у Settings.
- [x] Мігрувати лише порожній шлях або старий автоматичний `Документи\Pullora Apps`; будь-який інший наявний шлях вважати користувацьким і залишати без змін. Прибрано старе спеціальне перепризначення `Program Files\Git`; тести фіксують міграцію порожнього й старого автоматичного шляху та збереження звичайного користувацького і Git-шляху.
- [x] Виконувати міграцію шляху атомарно: нова директорія готується до зміни runtime-стану, після чого оновлений шлях зберігається в `config.json`. Якщо підготовка або запис не вдається, Pullora повертає попередні налаштування; створена цією спробою порожня папка видаляється. Тест покриває успішний commit і відмову запису config.
- [x] Показувати ефективний шлях у Settings і дозволити змінити його через чинний системний вибір папки.
